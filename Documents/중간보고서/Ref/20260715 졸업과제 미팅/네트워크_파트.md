## 1. 요구조건 및 제약 사항 분석에 대한 수정 사항

### 1-1. MQTT 브로커

**1. 제약 사항**
초기에는 Docker 없이 빠르게 개발하기 위해 Python 기반 개발용 브로커(amqtt)를 사용하였다. 그러나 다른 기기(다른 노트북·ESP32)가 LAN을 통해 발행한 메시지가 구독자인 백엔드에 전달되지 않는 문제가 발견되었다. 서버 자신(127.0.0.1)이 발행한 메시지는 정상 수신되었으나, 원격 기기의 발행만 누락되어 다중 기기 수집이 불가능하였다.

**2. 수정 사항**
브로커를 도청 도구(sniff)로 직접 검증하여 "브로커는 연결·발행을 수신하나 구독자에게 전달하지 않는" 현상을 특정하였고, 개발용 브로커의 한계로 판단하였다. 이에 운영용 표준 브로커인 **Mosquitto로 교체**하여 문제를 해결하였으며, 이후 원격 기기가 발행한 메시지가 백엔드까지 정상 라우팅되고 데이터베이스에 저장됨을 확인하였다.

### 1-2. 노드 위치 데이터 처리

**1. 제약 사항**
초기 설계는 센서의 위치를 고정 메타데이터(별도 테이블)로 한 번만 등록하는 구조였다. 그러나 그래픽스 파트로부터 **이동하는 노드의 위치(x, y, z)와 회전(쿼터니언 w, x, y, z)을 매 측정 시점마다** 제공받아야 한다는 요구가 추가되었다.

**2. 수정 사항**
RSSI 측정 메시지 스키마에 위치(`pos_x/y/z`)·회전(`rot_w/x/y/z`) 필드를 선택 항목으로 추가하고, 원시 측정 테이블(`rssi_raw`)에 해당 컬럼을 확장하였다. 또한 실시간 동기화 프레임에도 노드별 pos/rot을 포함하도록 수정하여, 그래픽스 파트가 이동 노드를 실시간으로 3차원 배치할 수 있도록 하였다. 기존 데이터 보존을 위해 스키마 마이그레이션은 컬럼 자동 추가 방식으로 처리하였다.

### 1-3. 네트워크 환경

**1. 제약 사항**
학교 공용 WiFi 환경에서 기기 간 직접 통신이 차단(AP Isolation)되어, 다른 노트북이나 보드가 서버에 접속하지 못하는 문제가 있었다. TCP 연결은 이루어지나 데이터 전달이 되지 않는 형태로 나타났다.

**2. 수정 사항**
개인 핫스팟 및 별도 공유기로 사설망을 구성하여, 모든 기기가 동일 LAN에서 통신하도록 변경하였다. 공유기 사용 시 서버 노트북의 IP를 DHCP 예약으로 고정하고, 방화벽에서 MQTT(1883)·백엔드(8000) 포트를 개방하여 안정적인 다기기 접속 환경을 확보하였다.

### 1-4. 그래픽스 실시간 연동 방식 (WebSocket)

**1. 제약 사항**
그래픽스 파트가 실시간 프레임을 수신하기 위해 WebSocket 주소(`ws://<서버IP>:8000/frames`)를 브라우저 주소창에 직접 입력하였으나, 브라우저는 `ws://` 스킴을 페이지로 열 수 없어 `ERR_UNKNOWN_URL_SCHEME` 오류가 발생하며 접속에 실패하였다(**그림 1**).

**2. 수정 사항**
WebSocket은 주소창으로 접근하는 웹페이지가 아니라 **코드 또는 전용 클라이언트로 연결하는 통신 프로토콜**임을 확인하였다. 이에 `wscat` 및 애플리케이션의 WebSocket 클라이언트(`new WebSocket(...)`)를 통해 `ws://<서버IP>:8000/frames`에 접속하도록 안내하여, 정상적으로 실시간 프레임을 수신함을 확인하였다. 파트 간 혼선을 막기 위해 연동 규격 문서에도 이 접속 방식을 명시하였다.

> **[그림 1] WebSocket 주소를 브라우저에 직접 입력했을 때의 접속 오류 (`ERR_UNKNOWN_URL_SCHEME`)**
> *(첫 번째 스크린샷 삽입 — 오류 화면)*

## 2. 설계 상세화 및 변경 내역

수집–동기화–저장–전달로 이어지는 데이터 파이프라인을 다음과 같이 상세화하였다.

a. **노드 발행**
   i. 고정 ESP32 센서 노드 및 게이트웨이 노드가 와이파이 RSSI를 측정한다.
   ii. 개별 노드는 `rssi/<node_id>`, 게이트웨이는 여러 노드를 묶어 `gateway/<gw_id>`로 MQTT 발행한다.
   iii. 메시지에는 노드 ID·타임스탬프·RSSI·시퀀스 번호와, 이동 노드의 경우 위치·회전을 포함한다.

b. **메시지 수집 (Mosquitto)**
   i. Mosquitto 브로커가 다수 노드의 발행을 동시에 수집한다.
   ii. 백엔드는 `rssi/#`, `gateway/#`, `status/+/lwt` 토픽을 구독한다.

c. **검증 및 필터링**
   i. JSON 형식·필수 필드·RSSI 범위(−100~−10 dBm)·타임스탬프 오차를 점검한다.
   ii. 시퀀스 번호로 노드별 패킷 손실을 집계한다.

d. **시간 동기화**
   i. 근접 시각의 측정값을 200ms 타임 윈도우로 묶어 하나의 프레임으로 구성하고, 결측 노드를 함께 표기한다.

e. **데이터 저장 (PostgreSQL)**
   i. 원시 측정값·동기화 프레임·노드 상태를 저장하며, 원시값은 배치 삽입으로 부하를 완화한다.

f. **실시간 전달 (WebSocket)**
   i. 동기화 프레임을 WebSocket(`/frames`)으로 그래픽스 파트에 실시간 push한다.

g. **상태·성능 모니터링**
   i. LWT와 하트비트로 노드 온/오프라인을 추적하고, 수집 지연·손실률·프레임 생성 시간을 계측한다.

**주요 변경 내역:** ① 개발용 브로커(amqtt) → **Mosquitto**로 교체, ② 게이트웨이 배치 메시지 지원 추가, ③ 이동 노드 대응을 위한 **위치·회전(pos/rot) 필드** 도입.

### 2-1. 임베디드·그래픽스 간 메시지 규약 (합의)

임베디드 파트와 그래픽스 파트 사이에서 주고받는 메시지 형식을 다음과 같이 합의하였다. 임베디드는 평면 필드로 발행하고, 백엔드는 이를 검증·동기화한 뒤 그래픽스가 사용하기 쉬운 중첩 구조로 재구성하여 전달한다.

**① 임베디드 → 서버 (MQTT 발행, 토픽 `rssi/<node_id>`)**
```json
{
  "node_id": "node-01",
  "timestamp": 1751000000000,
  "rssi": -58,
  "seq": 10,
  "pos_x": 1.2, "pos_y": 0.0, "pos_z": 2.4,
  "rot_w": 1, "rot_x": 0, "rot_y": 0, "rot_z": 0,
  "status": 0
}
```

**② 서버 → 그래픽스 (WebSocket 프레임 내 노드 항목)**
```json
"node-01": {
  "rssi": -58,
  "seq": 10,
  "server_receive_ms": 1751000000560,
  "pos": {"x": 1.2, "y": 0.0, "z": 2.4},
  "rot": {"w": 1, "x": 0, "y": 0, "z": 0}
}
```

백엔드는 임베디드의 평면 필드(`pos_x` 등)를 그래픽스가 3차원 배치에 바로 사용할 수 있는 중첩 객체(`pos`/`rot`)로 변환하고, 서버 수신 시각(`server_receive_ms`)을 함께 제공하여 지연 계산과 동기화에 활용하도록 하였다.

## 5. 보고 시점까지의 과제 수행 내용 및 중간 결과

### 5-1. MQTT 수집 파이프라인 (Mosquitto)

Mosquitto 브로커를 서버에 구성하여 다수의 노드가 동시에 접속·발행할 수 있는 메시지 허브를 구축하였다. 백엔드는 노드별 개별 메시지(`rssi/<id>`)와 게이트웨이 배치 메시지(`gateway/<gw>`)를 모두 처리하며, 배치 메시지는 각 노드 단위로 분해하여 동일 파이프라인에 투입한다. 임베디드 발행 시점의 서버 실행 로그는 **그림 2**와 같으며, 원격 기기(192.168.0.31)와 로컬(127.0.0.1)의 요청을 동시에 안정적으로 처리하고 있음을 확인할 수 있다.

향후에는 익명 접속을 계정 인증으로 전환하여 보안을 강화할 예정이다.

### 5-2. 검증·필터링 및 시간 동기화

수신 메시지에 대해 형식·필드·RSSI 범위·타임스탬프를 검증하고 이상 데이터를 필터링하며, 시퀀스 번호로 패킷 손실을 집계한다. 근접 시각의 측정값은 200ms 타임 윈도우로 묶어 결측 노드 정보와 함께 프레임으로 구성하여, 그래픽스 파트가 일관된 스냅샷을 입력받도록 하였다. 핵심 로직(동기화·손실 집계·상태 관리)에 대한 단위 테스트를 작성하여 회귀 검증 기반을 마련하였다.

### 5-3. PostgreSQL 저장 설계 및 결과

원시 측정값(`rssi_raw`), 동기화 프레임(`frame`), 노드 상태(`node_status`), 노드 위치 메타(`node_meta`) 테이블을 설계하였다. 원시 측정값은 매 메시지 개별 연결 대신 큐 기반 배치 삽입으로 저장하여 노드 수 증가에 대비하였으며, 이동 노드 대응을 위해 `rssi_raw`에 위치·회전 컬럼을 추가하였다. 실제 발행 데이터가 저장된 결과는 **그림 3**과 같으며, 노드별 저장 건수의 합(141+139+140+144+144 = **708건**)이 아래 모니터링 화면(그림 4)의 수신·저장 건수와 정확히 일치하여 **손실 없는 저장**을 확인하였다.

### 5-5. 다기기 통합 실증

물리적으로 분리된 **실물 임베디드 게이트웨이(STM32/ESP32)** 가 서버에 접속하여 RSSI를 발행하고(그림 2), 이 데이터가 백엔드를 거쳐 **PostgreSQL에 저장(그림 3)됨과 동시에 실시간 모니터링에 반영(그림 4)되고 그래픽스 파트에 WebSocket으로 전달**되는 전 구간을 실측으로 검증하였다. 임베디드·그래픽스 양측과 메시지 규약(토픽·필드·위치/회전 형식)도 각각 합의를 완료하였다. 이 과정에서 브로커·방화벽·네트워크·연동 방식 문제를 단계적으로 진단하여 해결하였다. 다만 임베디드 발행 측에서 시퀀스 증가 기준·전송 주기로 인한 패킷 손실이 관측되어, 발행 로직 개선은 후속 과제로 남는다.

### 향후 계획

실물 게이트웨이(STM32/ESP32) 연동과 임베디드·그래픽스 양측의 메시지 규약 합의는 완료하였다. 향후에는 현재 관측된 패킷 손실을 개선하기 위해 임베디드 발행 로직(시퀀스 증가 기준·전송 주기·QoS)을 협의·조정하고, 다중 실물 노드로 확장하여 실측 성능을 재측정할 예정이다. 또한 MQTT 인증 및 데이터베이스 접근 보안을 강화하고, 착수 단계에서 보류한 위치 추정(PositionEstimate) 기능의 알고리즘을 구체화할 계획이다.
